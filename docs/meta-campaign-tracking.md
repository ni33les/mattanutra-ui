# Meta campaign tracking

The browser and server send only enabled acquisition milestones. `Purchase` comes from verified payment confirmation, with the saved total and currency; receipt pages and arbitrary BPM events cannot create it. Retail webhooks confirm basket payments even when the browser closes. Retail/MCP projections share the Stripe session conversion identity.

| Environment | Event names | Required parameter |
| --- | --- | --- |
| DEV | `DEV_PageView`, `DEV_Purchase`, etc. | `mn_env=dev` |
| UAT | `UAT_PageView`, `UAT_Purchase`, etc. | `mn_env=uat` |
| PRD | `PageView`, `Purchase`, etc. | `mn_env=prd` |

Set `MATTANUTRA_ENV`, `META_TRACKING_ENABLED=true`, `FACEBOOK_PIXEL_ID_DEV/UAT/PRD` and `FACEBOOK_CAPI_ACCESS_TOKEN_DEV/UAT/PRD` in the corresponding runtime. DEV/UAT require both environment-specific credentials and a dataset distinct from every known production pixel ID. Generic/public fallback credentials are production-only. Missing credentials or a shared production destination disable capture and delivery in DEV/UAT, including the header Pixel. Event prefixes, Test Events codes and legacy `FACEBOOK_ALLOW_SHARED_PIXEL` flags cannot bypass this isolation. Configure separate DEV/UAT datasets before enabling those environments. Optional `FACEBOOK_CAPI_TEST_EVENT_CODE_DEV/UAT` directs diagnostics to Meta Test Events. Tokens remain server-only. The locale layout reads public configuration and the saved preference per request, so build-time settings and another visitor's opt-out cannot leak through the full-route cache. This makes locale documents dynamic. Published library summaries, article content, translation links and homepage testimonials use separate 300-second data caches; those caches contain only public content and never visitor cookies, preferences or tracking data. Admin content reads remain uncached.

Before enabling a runtime, apply `npm run marketing:schema:apply` using its schema role and grant its runtime role SELECT/INSERT/UPDATE/DELETE on the three `meta_*` tables. The additive migration never changes existing assessment, product, payment or financial records. Deploy the web application and workers from the same revision; the hosting worker must advertise `send_meta_event`. Disabling the flag stops new capture and delivery; use existing task retry controls when deliberately resuming failed delivery tasks.

Customer funnel events include PageView, ViewContent, QuizStart, QuizProgress (25/50/75%), Lead, EmailCapture, Contact, SelectOffer, AddToCart, InitiateCheckout, OrderSubmitted and Purchase. A quiz view is not a start. For `web-products-v1`, server-confirmed assessment capture emits the sole `Lead`, without waiting for the optional HealthScore. Historical journeys retain their first-usable-HealthScore `Lead` meaning; historical events are not replayed or relabeled. `QuizSubmitted` is retired: submission remains in internal assessment/BPM records, new exports are refused, pending server copies are suppressed, and browser receipts omit it. Historical accepted events are preserved. Campaign completion counts use `Lead`. Checkout is counted only after a usable attempt exists. The free web reveal sends `ViewContent` separately with `funnel_stage=formula` and `funnel_stage=products`, only when current content is displayed. Loading routes, animated phases and worker completions do not count as views. The capture endpoint validates the bound assessment revision, formula version and current product run. Browser/CAPI copies reuse the durable server event ID across reloads and tabs. Suggested/default-selected products and product toggles do not raise `AddToCart`; explicitly continuing with a nonempty validated subset does, once per active run and selected subset, using the stored recommendation subtotal. Checkout retains its independently validated payable quote. Business events such as worker completion, accounting and administrative notices remain internal.

The explicit event payload policy reconstructs custom data. Permitted fields are environment/schema, the allowlisted journey version, locale/channel/stage, opaque plan and numeric campaign IDs, offer, purchase type, coarse progress and appropriate amounts/currency. Every new CAPI event, including PageView, ViewContent and Lead, snapshots the available customer identifiers from its enabled, unexpired tracking context and already-bound assessment/payment/checkout records. A single bounded lookup prefers the event’s verified resource; otherwise it reads the latest bound resource of each kind and fills missing contact fields only for compatible identities. Verified payment contact takes precedence over another checkout in the same browser. Browser-supplied plan IDs cannot select customer identities. Email, phone, first name, country, city, region and postcode are normalized and SHA-256 hashed into `user_data` when known; no new contact form is introduced. The hash-only allowlist also supports separately supplied surname, gender and full date of birth, but current customer records do not provide those fields: full delivery names are not split, biological sex is not exported as gender, and age is not converted into a guessed birthday. Existing event snapshots are not retroactively enriched, and withdrawal clears matching hashes and suppresses queued events. Matching also uses a stable hashed tracking-context ID, an additional hashed plan ID when available, original browser/ad-click identifiers, browser IP and user agent. The context ID links landing visits and buy-before-quiz purchases without requiring a plan. Raw contacts, names, addresses, answers, scores, conditions, supplement/product identities, contents and capability URLs are not added to custom data. CAPI source URLs retain recognized generic paths and valid plan IDs; other parameters and fragments are removed. Raw fields are never copied from BPM or payment-provider request headers. Native Pixel is a separate browser collector: it reads actual page URLs and referrers, including query strings, fragments and capability URLs. The server/custom-data allowlist does not sanitize those native fields. Automatic configuration remains disabled.

`Purchase` remains the standard Meta event in PRD. Plan payments include `purchase_type=plan` and the saved `offer=precision|pro`; product orders include `purchase_type=products`. Both include the actual paid `value` and ISO `currency`, `channel=web|retail|mcp`, locale and `mn_env`. The payment amount is checked against the provider before publication. Offer selection, basket additions and checkout events also carry the purchase type. A flow describes the originating journey; an online retail checkout still uses `action_source=website`. Do not send item names or IDs to enable catalog ads.

Internal live test purchases must carry `internal_test: true` in the saved payment metadata, or `internal_test="true"` on the trusted Stripe Checkout Session / expanded PaymentIntent before its first confirmation. Confirmation persists the flag, and retries cannot clear it. These payments still fulfill normally but do not enqueue `Purchase`, so no browser Purchase receipt is created either. The retail-to-MCP projection preserves this exclusion. Production Stripe test/mock payments remain excluded. A marker added after Meta already accepted an event cannot retract that event; no historical events are relabeled or backfilled.

Usable plan and product checkouts also enqueue `InitiateCheckout` on the server with the saved value and currency. That durable event survives the customer closing the browser after checkout creation. The browser receives the existing checkout event ID and authoritative custom data, so its native copy uses the same ID, amount and currency instead of creating another conversion. A marketing capture failure does not fail an otherwise usable payment session; browser capture can recover the saved checkout only after verifying its provider session and binding to the current tracking context. Client-invented attempt IDs and amounts cannot create checkout events. Verified payment confirmation remains the authority for `Purchase`.

Confirmed `Purchase`, `Lead`, `EmailCapture`, `OrderSubmitted` and `McpConnectionVerified` events also have browser copies. A read-only, same-origin receipt endpoint returns only the current enabled tracking context's latest 50 milestones from the last ten minutes. It never exposes contact/matching data or permits the browser to create confirmed milestones. The visible customer page polls every five seconds after the Meta SDK loads, pauses while hidden, resumes after a payment return, and stops on withdrawal. Receipt IDs are reused as native `eventID` values; local storage and browser locks prevent repeated sends across polls, reloads and tabs. Only production `Purchase` and `Lead` use standard event commands; nonproduction names remain prefixed. A blocked SDK, closed browser, expired window or payment completed entirely outside the website can still yield only CAPI delivery. Both delivery methods support ad measurement; CAPI remains the durable confirmation path.

Pharmacy pay-at-till orders enqueue the custom `OrderSubmitted` event in the same transaction as the saved unpaid order. It uses the validated order total/currency, `purchase_type=products`, `channel=retail`, locale and the assessment's tracking context. Replaying an order produces no duplicate; a new order has its own event. The browser cannot manufacture this server milestone. These orders do not emit `Purchase`: counter settlement has no verified application callback yet, and submitting an unpaid order is not payment evidence.

In Ads Manager, append these to the ad's URL parameters field (without a leading question mark):

```text
campaign_id={{campaign.id}}&adset_id={{adset.id}}&ad_id={{ad.id}}
```

Only resolved numeric IDs are saved. Use the published ad's actual landing URL to check expansion; unresolved macros are ignored. `creative_id` is accepted only when supplied as a real numeric ID; no creative macro is invented. Capture happens during initial preference setup and when an already-enabled visitor arrives through a new ad, before PageView. Untagged navigation/checkout recovery retains the last captured ad. A new tagged ad replaces the entire ID group; a new click without IDs clears the old group instead of assigning it to the old campaign. Repeated events preserve the original `fbc` timestamp. Server resource bindings preserve the saved context when checkout completes without the original browser cookies. Unrelated visits in a new browser cannot be joined without an existing resource binding; no browser identities are fabricated to fill gaps.

Advertising measurement starts automatically, without a landing-page popup. Existing opt-outs are preserved. The Privacy page has an Advertising preferences control; turning it off suppresses pending deliveries and clears matching data. The context records `preference_source=site_default` for automatic activation and `explicit` for a user choice; automatic activation must not be described as explicit consent. The legacy `consent_granted` flag represents whether tracking is enabled. This site default is a product policy, not a determination that consent requirements in every visitor jurisdiction are satisfied. Contexts expire after 90 days. Both HTTPS production hostnames (`mattanutra.com` and `www.mattanutra.com`) are accepted for preference and event requests behind the hosting proxy. Apply the additive `preference_source` column before deploying this version. Native Pixel covers every customer page in each registered language, including assessment, results, plan and product checkout, payment return, order tracking, articles and connection pages. Admin and API paths remain excluded. Query parameters, fragments and incoming referrers do not disable it. Browser/CAPI copies use the same event name and ID.

For Pixel Helper or Meta's Event Setup Tool, either production hostname can be entered with `/` or a customer page. Root URLs automatically redirect to the preferred registered language, currently English (`/en`), Thai (`/th`) or Chinese (`/zh-CN`); native initialization occurs on the destination page. A saved opt-out keeps tracking off on every page. Ad IDs and free-text UTM parameters no longer gate browser detection, although only resolved numeric ad IDs enter explicit campaign fields.

The base code is a synchronous inline script in the initial HTML `<head>`, following [Meta's installation guide](https://developers.facebook.com/documentation/meta-pixel/get-started). It initializes the Pixel and queues the initial PageView while the browser parses the page, before React or any application API request. It checks the saved opt-out before loading Meta. A body `<noscript>` image provides the JavaScript-disabled fallback only on enabled customer pages without a saved opt-out. The proxy supplies a trusted page path for the server-side route exclusion. Event IDs are generated in the browser, never embedded as a shared cached value.

After hydration, preference/context capture continues with bounded retries. The first server PageView reuses the header event's UUID and does not send a second browser copy. Subsequent client navigations use distinct occurrences. Other browser funnel events retain receipt-authoritative IDs and checkout values. Event capture retries network failures, HTTP 429 and server errors up to three attempts, using an eight-second request timeout, 500 ms then 1,500 ms delays, and the same event ID and source URL. Rejected receipts do not mark an event as sent, and delayed native copies are skipped after navigation. The initial native PageView is independent of these requests, so a backend outage does not prevent Pixel detection. For a detection failure, inspect the raw header, `connect.facebook.net/en_US/fbevents.js` and browser tracking protection first. The Campaigns dashboard's accepted delivery counts show CAPI receipts separately from browser detection and do not establish authenticated Event Setup Tool success.

The customer-page CSP permits the exact Event Setup Tool script `https://www.facebook.com/signals/iwl.js`, in addition to `connect.facebook.net`. Meta's bootstrap uses a message handshake and then loads that authenticated script; its URL can contain an access token and must not be copied into logs or reports. Customer `connect-src` permits native Pixel delivery to Meta and same-origin capture but blocks the configured OpenBridge primary and fallback gateways. The application outbox is the single intended CAPI sender; its worker HTTP requests are unaffected by browser CSP. Disconnect the redundant OpenBridge integration in Meta Events Manager as well: it remains configured externally and produces expected CSP console messages until disconnected. The two gateway domains are a primary/fallback pair, not evidence of two independent server sends. Frame permissions are unchanged; admin/API documents retain their restrictive CSP. Meta can suppress automated headless-browser traffic, so an absent native request in an automated smoke test is not sufficient evidence of a customer-browser failure.

Before validating a released fix, confirm that DigitalOcean's live deployment uses the intended Git commit. A configuration-only rebuild can reuse the previous source revision; use Actions → Deploy to fetch the latest branch revision, and enable `github.deploy_on_push` for subsequent pushes. Avoid static runtime overrides for `AGENTIC_BUILD_ID`, `AGENTIC_WORKER_VERSION`, and `WORKER_VERSION`: the application derives these from its compiled revision, and stale overrides intentionally prevent startup. The `x-agentic-build-id` response header on `/api/mcp` identifies the application revision actually serving requests.

An outbox row and delivery task commit with payment confirmation. Provider HTTP runs outside database transactions. An expiring claim prevents concurrent dispatch; retries retain ID/time, stop after nine provider attempts, and do not export events older than six days. New events snapshot matching evidence at enqueue, so later ad visits cannot rewrite a pending purchase's click/browser data. Opt-out clears matching snapshots and suppresses pending deliveries. Apply the additive `meta_conversion_events.matching` column and reporting index before the application/worker rollout. Existing rows retain their previous context-based delivery behavior; no historical matching snapshot or purchase is fabricated. Acknowledgement requires both HTTP success and `events_received=1`. No historical backfill is performed.

Marketing → Campaigns shows environment/destination, delivery status totals and purchase reconciliation for the selected date range. The Meta section has its own campaign/ad ID, flow and language filters. It groups recorded purchases by purchase type, offer and currency; values are gross confirmed purchase amounts, not net revenue or ad-attributed revenue. Historic missing fields remain unspecified. Visitor activity counts unique tracking contexts with a PageView in the same date range, flow, language and campaign/ad group; milestones each count those visitors once without inferring missing earlier steps. The displayed product purchase rate is product-purchasing visitors divided by those visitors. Formula views, product views, confirmed baskets and product checkouts are separate columns; historical plan purchases remain available in the sales table. The sales table also includes purchases without a PageView in the period. Tables cap at 200 groups and disclose truncation; narrow the date range for omitted groups. These are observed activity cohorts, not Meta attribution-window reports or a strict sequential funnel.

Acceptance is not proof of attribution or campaign eligibility. Ads-attributed purchases, spend, CPA and ROAS remain explicitly unavailable until an Ads reporting integration exists. In the Meta account, select the production dataset and standard `Purchase` for sales optimisation. If useful, create offer-specific custom conversions using `purchase_type=plan` plus `offer=precision|pro`, and `channel` for the flow. Verify actual Events Manager diagnostics, dataset category/restrictions, event match quality and conversion eligibility. These application changes do not configure the ad account or change campaign budgets. Never relabel health events to evade Meta restrictions. A CAPI token may send events while lacking permission to read pixel settings.

Validation covers explicit payload allowlisting, customer-page coverage, server environment authority, real payment/outbox transactions and rollback, Precision/Pro categorisation, durable checkout values, duplicate receipts and confirmations, retail/MCP deduplication, bounded retries, navigation changes, immutable click snapshots, competing context writers and withdrawal, reporting cohorts/currencies, opt-out preservation and preference changes. Browser checks cover registered languages, root redirects, customer funnels, Event Setup Tool/gateway CSP, internal-page exclusion, mobile tables, filters and clipboard failure. Tests use an isolated database and mocked provider delivery; they establish application behavior, not Meta account attribution. Production smoke tests must not manufacture purchases.

For release verification, confirm the live build revision, then use Meta Test Events on the separate test dataset to compare browser `eventID` with CAPI `event_id` and `event_name` for one action. Retries must reuse the same receipt and ID. Check the account Diagnostics issue and connection-method breakdown directly: aggregate totals alone cannot establish a threefold duplication rate or validate ad attribution. Reconcile customer purchases against Stripe and stored orders.
