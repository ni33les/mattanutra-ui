# Meta campaign tracking

The browser and server send only enabled acquisition milestones. `Purchase` comes from verified payment confirmation, with the saved total and currency; receipt pages and arbitrary BPM events cannot create it. Retail webhooks confirm basket payments even when the browser closes. Retail/MCP projections share the Stripe session conversion identity.

| Environment | Event names | Required parameter |
| --- | --- | --- |
| DEV | `DEV_PageView`, `DEV_Purchase`, etc. | `mn_env=dev` |
| UAT | `UAT_PageView`, `UAT_Purchase`, etc. | `mn_env=uat` |
| PRD | `PageView`, `Purchase`, etc. | `mn_env=prd` |

Set `MATTANUTRA_ENV`, `META_TRACKING_ENABLED=true`, `FACEBOOK_PIXEL_ID_DEV/UAT/PRD` and `FACEBOOK_CAPI_ACCESS_TOKEN_DEV/UAT/PRD` in the corresponding runtime. Environment-specific credentials take precedence over generic credentials. Pixel IDs may be different; prefixes also isolate non-production events when sharing a dataset. Do not configure production campaigns/custom conversions to include prefixed test events. Optional `FACEBOOK_CAPI_TEST_EVENT_CODE_DEV/UAT` directs diagnostics to Meta Test Events. Tokens remain server-only. Runtime public configuration is fetched so static builds cannot embed another environment's enabled state.

Before enabling a runtime, apply `npm run marketing:schema:apply` using its schema role and grant its runtime role SELECT/INSERT/UPDATE/DELETE on the three `meta_*` tables. The additive migration never changes existing assessment, product, payment or financial records. Deploy the web application and workers from the same revision; the hosting worker must advertise `send_meta_event`. Disabling the flag stops new capture and delivery; use existing task retry controls when deliberately resuming failed delivery tasks.

The allowed events are PageView, ViewContent, QuizStart, QuizProgress (25/50/75%), QuizSubmitted, Lead, EmailCapture, Contact, SelectOffer, AddToCart, InitiateCheckout and Purchase. A quiz view is not a start; Lead means the first usable HealthScore; checkout is counted after a usable attempt exists. Suggested products do not automatically raise AddToCart. Business events such as worker completion, accounting and administrative notices remain internal.

The export policy reconstructs every payload. Permitted fields are environment/schema, locale/channel/stage, opaque plan and numeric campaign IDs, offer, purchase type, coarse progress and appropriate amounts/currency. Matching uses normalized SHA-256 contact hashes, a hashed plan ID, original browser/ad-click identifiers, browser IP and user agent. Raw contacts, names, addresses, answers, scores, conditions, supplement/product identities, contents and capability URLs are excluded. URLs retain recognized generic paths and valid plan IDs; other parameters and fragments are removed. Raw fields are never copied from BPM or payment-provider request headers.

`Purchase` remains the standard Meta event in PRD. Plan payments include `purchase_type=plan` and the saved `offer=precision|pro`; product orders include `purchase_type=products`. Both include the actual paid `value` and ISO `currency`, `channel=web|retail|mcp`, locale and `mn_env`. The payment amount is checked against the provider before publication. Offer selection, basket additions and checkout events also carry the purchase type. A flow describes the originating journey; an online retail checkout still uses `action_source=website`. Do not send item names or IDs to enable catalog ads.

In Ads Manager, append these to the ad's URL parameters field (without a leading question mark):

```text
campaign_id={{campaign.id}}&adset_id={{adset.id}}&ad_id={{ad.id}}
```

Only resolved numeric IDs are saved. Use the published ad's actual landing URL to check expansion; unresolved macros are ignored. `creative_id` is accepted only when supplied as a real numeric ID; no creative macro is invented. Capture happens during initial preference setup and when an already-enabled visitor arrives through a new ad, before PageView. Untagged navigation/checkout recovery retains the last captured ad. A new tagged ad replaces the entire ID group; a new click without IDs clears the old group instead of assigning it to the old campaign. Repeated events preserve the original `fbc` timestamp. Server resource bindings preserve the saved context when checkout completes without the original browser cookies. Unrelated visits in a new browser cannot be joined without an existing resource binding; no browser identities are fabricated to fill gaps.

Advertising measurement starts automatically, without a landing-page popup. Existing opt-outs are preserved. The Privacy page has an Advertising preferences control; turning it off suppresses pending deliveries and clears matching data. The context records `preference_source=site_default` for automatic activation and `explicit` for a user choice; automatic activation must not be described as explicit consent. The legacy `consent_granted` flag represents whether tracking is enabled. This site default is a product policy, not a determination that consent requirements in every visitor jurisdiction are satisfied. Contexts expire after 90 days. Both HTTPS production hostnames (`mattanutra.com` and `www.mattanutra.com`) are accepted for preference and event requests behind the hosting proxy. Apply the additive `preference_source` column before deploying this version. Native Pixel runs only on public home/legal pages with safe URLs/referrers and automatic configuration disabled. Personalized pages use the server export boundary. Browser/CAPI copies use the same event name and ID.

An outbox row and delivery task commit with payment confirmation. Provider HTTP runs outside database transactions. An expiring claim prevents concurrent dispatch; retries retain ID/time, stop after nine provider attempts, and do not export events older than six days. New events snapshot matching evidence at enqueue, so later ad visits cannot rewrite a pending purchase's click/browser data. Opt-out clears matching snapshots and suppresses pending deliveries. Apply the additive `meta_conversion_events.matching` column and reporting index before the application/worker rollout. Existing rows retain their previous context-based delivery behavior; no historical matching snapshot or purchase is fabricated. Acknowledgement requires both HTTP success and `events_received=1`. No historical backfill is performed.

Marketing → Campaigns shows environment/destination, delivery status totals and purchase reconciliation for the selected date range. The Meta section has its own campaign/ad ID, flow and language filters. It groups recorded purchases by purchase type, offer and currency; values are gross confirmed purchase amounts, not net revenue or ad-attributed revenue. Historic missing fields remain unspecified. Visitor activity counts unique tracking contexts with a PageView in the same date range, flow, language and campaign/ad group; milestones each count those visitors once without inferring missing earlier steps. Purchase rate is purchasing visitors divided by those visitors. The sales table also includes purchases without a PageView in the period. Tables cap at 200 groups and disclose truncation; narrow the date range for omitted groups. These are observed activity cohorts, not Meta attribution-window reports or a strict sequential funnel.

Acceptance is not proof of attribution or campaign eligibility. Ads-attributed purchases, spend, CPA and ROAS remain explicitly unavailable until an Ads reporting integration exists. In the Meta account, select the production dataset and standard `Purchase` for sales optimisation. If useful, create offer-specific custom conversions using `purchase_type=plan` plus `offer=precision|pro`, and `channel` for the flow. Verify actual Events Manager diagnostics, dataset category/restrictions, event match quality and conversion eligibility. These application changes do not configure the ad account or change campaign budgets. Never relabel health events to evade Meta restrictions. A CAPI token may send events while lacking permission to read pixel settings.

Validation covers payload allowlisting, URLs/referrers, server environment authority, real payment/outbox transactions and rollback, Precision/Pro categorisation, duplicate confirmations, retail/MCP deduplication, bounded retries, immutable click snapshots, competing context writers and withdrawal, reporting cohorts/currencies, opt-out preservation, preference changes and browser gating. Browser checks cover all three report languages, mobile tables, filters and clipboard failure. Tests use an isolated database and mocked provider delivery; they establish application behavior, not Meta account attribution. Production smoke tests must not manufacture purchases.
